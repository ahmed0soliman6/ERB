# وثيقة التصميم النهائي لنظام إدارة مخازن المجمع الطبي

**الإصدار:** 1.0 — تصميم لاعتماد المستخدم قبل بدء البرمجة  
**الحالة:** مسودة نهائية للمراجعة والاعتماد  
**نطاق الوثيقة:** التصميم فقط. لا تتضمن هذه الوثيقة كودًا أو ملفات مشروع.

## 1. القرار التنفيذي

النظام المقترح هو تطبيق Desktop محلي يعمل على جهاز كمبيوتر واحد، ويستخدم SQLite كقاعدة البيانات الوحيدة. لا يعتمد تشغيله على الإنترنت أو على خادم خارجي أو على Firebase أو Supabase أو أي قاعدة بيانات سحابية.

التقنية الأساسية المقترحة هي **C# مع .NET Framework 4.8 وWindows Forms**، مع نشر نسخة x86 مدمجة بالمكونات اللازمة. اختيار Windows Forms مقصود لتقليل استهلاك الموارد، وتجنب Browser/WebView، ودعم الأجهزة الضعيفة، وتوفير سلوك مستقر مع Windows 7 وWindows 8.1 وWindows 10 وWindows 11. توضح وثائق Microsoft أن .NET Framework 4.8 قابل للتثبيت على Windows 7 SP1 بنسختيه 32-bit و64-bit، وعلى Windows 8.1 وWindows 10، بينما تعرض SQLite رسميًا ملفات Windows x86 وx64 [1] [2].

> **شرط توافق مهم:** المقصود بـ Windows 7 هو Windows 7 SP1، والمقصود بـ Windows 8 في مصفوفة القبول هو Windows 8.1. أما Windows 8.0 الأصلي فليس مكافئًا لـ Windows 8.1 من ناحية دعم .NET Framework، ولذلك يجب اعتباره اختبار قبول منفصلًا قبل الالتزام به تجاريًا. إذا كان دعم Windows 8.0 إلزاميًا، فلا يبدأ التنفيذ قبل بناء نموذج توافق واختباره على جهاز حقيقي.

سيتم بناء النظام حول قاعدة صارمة:

> **Stock Movements = Single Source of Truth**

أي أن الرصيد لا يكون قيمة تشغيلية مستقلة قابلة للتعديل اليدوي. الرصيد يحسب من الحركات المعتمدة، بينما يمكن استخدام لقطات مؤقتة للأداء أو للتقارير بشرط أن تكون قابلة لإعادة البناء والتحقق.

## 2. حدود النظام

يدير النظام المخزن الرئيسي، ومخزن الطوارئ، ومخزن أدوية العمليات، ومخزن مستلزمات العمليات، وأي مخازن مستقبلية يضيفها المسؤول من الشاشة دون تعديل البرنامج.

يدعم النظام قائمة أصناف موحدة. الصنف الواحد يمكن أن يظهر في عدة مخازن، لكن لا ينشأ له سجل صنف جديد لكل مخزن. يدعم النظام التوريد، والتحويل، والصرف، والاستهلاك، والجرد، وتسويات الجرد، وبطاقة حركة الصنف، والتقارير، والمستخدمين والصلاحيات، وسجل التدقيق، واستيراد Excel، وتصدير Excel وPDF، والنسخ الاحتياطي والاستعادة، والترخيص المحلي الموقّع.

لا يتضمن الإصدار الأول مزامنة بين أجهزة أو تشغيلًا شبكيًا أو API. هذه ليست قيودًا مؤقتة؛ بل جزء من قرار Offline-Only.

## 3. التقنية النهائية ومبرراتها

### 3.1 طبقة التطبيق

يستخدم التطبيق بنية طبقية داخلية بسيطة:

- **Presentation:** واجهات Windows Forms باللغة العربية مع دعم RTL.
- **Application Services:** خدمات التوريد والتحويل والصرف والاستهلاك والجرد والاستيراد.
- **Domain:** قواعد الحركات، ومنع الرصيد السالب، واعتماد المستندات، وقواعد الترخيص.
- **Persistence:** طبقة SQLite واحدة مع معاملات Transactions واستعلامات parameterized.
- **Infrastructure:** النسخ الاحتياطي، التصدير، التوقيع والتحقق، وسجل التشغيل.

لن يتم استخدام Browser مفتوح أو WebView أو Node.js أو Python Runtime على جهاز العميل. سيتم تضمين SQLite ومكتبات التطبيق داخل حزمة التثبيت.

### 3.2 قاعدة البيانات

تستخدم SQLite في ملف قاعدة بيانات محلي واحد، مع تفعيل الخصائص التالية عند فتح الاتصال:

- `foreign_keys = ON` لضمان سلامة العلاقات.
- `journal_mode = WAL` إذا أثبت الاختبار توافقه مع بيئة Windows المستهدفة؛ وإلا يستخدم `DELETE` journal الأكثر تحفظًا.
- `busy_timeout` لمنع فشل العمليات بسبب قفل لحظي.
- معاملات صريحة لكل عملية تعتمد على أكثر من سجل.
- نسخ احتياطي عبر SQLite Online Backup أو نسخة آمنة بعد إغلاق الاتصال، وليس عبر نسخ ملف عشوائي أثناء الكتابة.

### 3.3 سبب عدم اختيار .NET الحديث

الإصدارات الحديثة من .NET لا تحقق شرط Windows 7؛ توضح وثائق Microsoft أن آخر إصدار حديث مدعوم على Windows 7 كان .NET 6، وانتهى دعمه في 12 نوفمبر 2024 [3]. لذلك لا يعتمد التصميم على .NET 8 أو .NET 9 أو .NET 10. كما لا يعتمد على WebView2 لأنه يضيف Runtime حديثًا ومتطلبات تثبيت لا تناسب شرط Windows 7 والأجهزة الضعيفة.

### 3.4 التوزيع

حزمة التثبيت المستهدفة هي Installer واحد قدر الإمكان ويحتوي على:

- ملفات البرنامج.
- مكتبة SQLite x86 للتشغيل على Windows 7 32-bit وعلى Windows 64-bit عبر WOW64.
- ملفات اللغة والقوالب.
- ملف Public Key للتحقق من الترخيص.
- أداة فحص وجود .NET Framework 4.8 Offline Installer أو تضمينه في الحزمة وفق سياسة التوزيع.
- اختصار البرنامج وملفات إلغاء التثبيت.

لا يضع البرنامج قاعدة البيانات داخل `Program Files`. يضعها في مسار بيانات قابل للكتابة مثل مجلد بيانات التطبيق المحلي، مع توفير مسار Backup يختاره المستخدم.

## 5. مبادئ البيانات

### 5.1 فصل أنواع البيانات

تنقسم قاعدة البيانات إلى ست مجموعات واضحة:

| المجموعة | وظيفتها |
|---|---|
| Master Data | الأصناف، الوحدات، التصنيفات، المخازن، الموردون، أسباب الحركات |
| Transaction Documents | مستندات التوريد والتحويل والصرف والاستهلاك |
| Stock Movements | الأثر الكمي النهائي لكل حركة معتمدة |
| Inventory Counts | جلسات الجرد ونتائج العد والفروقات |
| Audit and Security | المستخدمون، الأدوار، الصلاحيات، وسجل التدقيق |
| License and Backup | حالة الترخيص وبيانات النسخ الاحتياطي والاستعادة |

### 5.2 العلاقة بين المستند والحركة

المستند هو الحاوية التجارية أو التشغيلية التي يراجعها المستخدم. أما `stock_movements` فهو الأثر المحاسبي الكمي الناتج بعد اعتماد المستند.

قبل الاعتماد، يمكن أن يكون المستند في حالة Draft ولا ينتج أي حركة معتمدة. عند الضغط على Approve، ينفذ النظام معاملة واحدة تنشئ الحركات اللازمة وتغير حالة المستند إلى Approved. إذا فشل إنشاء أي حركة أو خالف أحد القيود، تفشل المعاملة كلها ولا يتغير المستند.

العلاقة تكون كالتالي:

```text
Document Header 1 ---- N Document Lines
Document Header 1 ---- N Stock Movements
Document Line   1 ---- N Stock Movements
Stock Movement  N ---- 1 Source Document
```

لا تخزن كميات مختلفة بين المستند والحركة. كمية السطر هي الكمية التي يُنتج منها أثر الحركة، والحركة تحمل `source_document_id` و`source_line_id` للرجوع إلى الأصل.

## 6. SQLite Schema النهائي

الأسماء التالية منطقية وثابتة. يمكن تغيير أسماء الأعمدة أثناء البرمجة لأسباب أسلوبية، لكن لا يجوز تغيير المعنى أو العلاقات دون مراجعة هذا التصميم.

### 6.1 Master Data

#### `warehouses`

- `id` — المفتاح الأساسي.
- `code` — رمز فريد مثل `MAIN` أو `ER`.
- `name` — اسم المخزن.
- `warehouse_type` — نوع إداري اختياري.
- `is_active` — حالة الاستخدام.
- `notes` — ملاحظات.
- `created_at`, `updated_at`.

#### `categories`

- `id`.
- `parent_id` — يسمح بتصنيف هرمي.
- `code`.
- `name`.
- `is_active`.

#### `units`

- `id`.
- `code` — قيمة موحدة مثل `PCS`, `BOX`, `AMP`, `VIAL`, `BAG`.
- `name_ar`.
- `name_en` اختياري.
- `is_active`.

لا تسجل الملاحظات داخل الوحدة. عبارات مثل «كيس كامل إضافة» أو «50 جنيه» لا تكون وحدات، بل تحفظ في `notes` أو في ملاحظة المستند.

#### `items`

- `id`.
- `sku` — فريد بعد إزالة الفراغات الزائدة.
- `name_ar`.
- `normalized_name` — نسخة تطبيع للمقارنة ومنع التكرار.
- `category_id`.
- `base_unit_id`.
- `notes`.
- `minimum_stock`.
- `expiry_tracking`.
- `is_active`.
- `created_at`, `updated_at`.

يمنع النظام التكرار من خلال فحص `sku` وفحص الاسم المطبّع. لا يعتمد المنع على الاسم وحده إذا قرر المسؤول أن صنفين متشابهين يختلفان في التركيز أو الحجم أو الوحدة؛ عندها يُطلب SKU مختلف وبيانات وصفية واضحة.

#### `item_warehouse_settings`

- `is_allowed`.
- `notes`.

### 6.3 `stock_movements`

هذا هو جدول الحقيقة الكمية. يحتوي كل سجل على:

- `id`.
- `movement_no` — رقم حركة فريد.
- `movement_type` — `OPENING`, `RECEIPT`, `TRANSFER`, `ISSUE`, `CONSUMPTION`, `COUNT_ADJUSTMENT`.
- `item_id`.
- `warehouse_id`.
- `quantity` — كمية موجبة في السجل.
- `direction` — `IN` أو `OUT`.
- `signed_quantity` — قيمة مشتقة أو محفوظة بقيد، موجبة للدخول وسالبة للخروج.
- `unit_id`.
- `source_warehouse_id` اختياري.
- `destination_warehouse_id` اختياري.
- `source_document_type`.
- `source_document_id`.
- `source_line_id`.
- `reason_id`.
- `user_id`.
- `occurred_at`.
- `created_at`.
- `notes`.
- `reversal_of_movement_id` اختياري.

قواعد هذا الجدول:

1. لا يسمح النظام بتعديل كمية حركة معتمدة.
2. لا يحذف النظام حركة معتمدة حذفًا فعليًا.
3. التصحيح يتم بحركة عكسية مرتبطة بالحركة الأصلية.
4. التحويل ينتج سجل خروج من المصدر وسجل دخول إلى الوجهة داخل نفس المعاملة.
5. لا ينتج المستند Draft حركات في هذا الجدول.
6. لا يسمح `source_document_id` بأن يشير إلى مستند غير معتمد.

## 7. دورة الحركة من البداية إلى النهاية

### 7.1 التوريد

ينشئ المستخدم مستند توريد Draft، ويحدد المورد والمخزن والأصناف والكميات والوحدات. يتحقق النظام من الأصناف والوحدات والقيم الموجبة. عند الاعتماد، ينشئ سجل `RECEIPT` داخل `stock_movements` لكل سطر، ثم يغير حالة المستند إلى Approved داخل Transaction واحدة.

### 7.2 التحويل

ينشئ المستخدم مستند تحويل يحدد المصدر والوجهة والأصناف والكميات. قبل الاعتماد يحسب النظام الرصيد المتاح. عند الاعتماد ينفذ:

```text
BEGIN TRANSACTION
  تحقق من صلاحية المستند ومنع الرصيد السالب
  أنشئ حركة OUT للمخزن المصدر لكل سطر
  أنشئ حركة IN للمخزن الوجهة لكل سطر
  اربط الحركتين بالمستند نفسه
  غيّر المستند إلى APPROVED
COMMIT
```

إذا فشل أي تحقق أو حدث خطأ في أي خطوة، يتم `ROLLBACK` ولا يبقى خروج دون دخول.

### 7.3 الصرف والاستهلاك

الصرف حركة خروج من مخزن إلى جهة أو مستخدم. الاستهلاك حركة خروج مرتبطة بمنطقة أو إجراء أو قسم. الفرق بينهما تشغيلي في المستند والتقرير، بينما كلاهما يترك أثرًا واضحًا في `stock_movements`.

### 7.4 الإلغاء والتصحيح

يمكن إلغاء مستند Draft. أما المستند Approved فلا يحذف. إذا كان إبطاله مطلوبًا، ينشئ النظام مستند عكس أو حركات عكسية موثقة مرتبطة بالمستند الأصلي، ويظهر ذلك في Audit Log.

## 8. سياسة الرصيد السالب

يمنع النظام الرصيد السالب افتراضيًا. يجب أن يحدث الفحص داخل نفس المعاملة التي تنشئ الحركة حتى لا تتجاوز عمليتان متتاليتان الرصيد نتيجة فحص منفصل قديم.

إذا تقرر السماح الاستثنائي لاحقًا، فلا يكون ذلك إعدادًا عامًا غير مراقب. يجب أن يتطلب:

- صلاحية خاصة.
- سببًا إلزاميًا.
- تسجيلًا في Audit Log.
- ظهورًا في تقرير الاستثناءات.
- إعدادًا يمكن تعطيله افتراضيًا.

## 9. نظام الجرد

يمر الجرد بالمراحل التالية:

1. إنشاء جلسة جرد لمخزن محدد.
2. التقاط الرصيد الدفتري لكل صنف.
3. إدخال الكمية الفعلية دون تعديل الرصيد الدفتري يدويًا.
4. حساب الفرق تلقائيًا.
5. مراجعة الأصناف ذات الفرق.
6. اعتماد الجلسة من مستخدم مخول.
7. إنشاء `COUNT_ADJUSTMENT` لكل فرق غير صفري.
8. إغلاق الجلسة ومنع إعادة اعتمادها.

الكمية الفعلية لا تستبدل حركة سابقة. الفرق فقط هو الذي يدخل كسجل جديد.

## 10. استيراد Excel والهجرة من الملف الحالي

لا يستورد البرنامج الملف الحالي اعتمادًا أعمى. ينفذ الاستيراد عبر معالج من خمس مراحل:

### المرحلة الأولى: اختيار الملف وقراءة الأوراق

يعرض النظام أسماء الأوراق، وعدد الصفوف، والعناوين المكتشفة، ويعتبر اسم الورقة مثل `مخازن 29-4-2026` وصفًا للمصدر لا تاريخ حركة تلقائيًا.

### المرحلة الثانية: Mapping

يطلب النظام ربط الأعمدة مع الحقول المعروفة، مثل اسم الصنف، والكمية الافتتاحية، والوحدة، والمخزن. يمكن حفظ Mapping لكل قالب Excel لاحقًا.

### المرحلة الثالثة: Validation

يفحص النظام:

- الأصناف المكررة.
- اختلافات الكتابة والمسافات.
- الوحدات غير المعروفة.
- الأصناف بلا رقم أو بلا اسم.
- الصفوف التي تمثل عناوين تصنيفية وليست أصنافًا.
- الصفوف ذات الترقيم المفقود.
- الكميات السالبة أو غير الرقمية.
- الخلايا الفارغة.
- التواريخ غير الصالحة.
- مشكلة ورقة الطوارئ التي تحتوي على متبقي محسوب من إجمالي فارغ.

### المرحلة الرابعة: المراجعة

يعرض النظام قائمة مشاكل قابلة للتصفية. لكل مشكلة قرار واضح: قبول، تصحيح، دمج مع صنف موجود، إنشاء SKU جديد، تجاهل الصف، أو إيقاف الاستيراد.

### المرحلة الخامسة: الترحيل

بعد اعتماد المراجعة، ينشئ النظام الأصناف والمخازن والوحدات اللازمة، ثم يحول الأرصدة التي لا تملك تاريخ حركة حقيقيًا إلى مستند `OPENING` أو `Imported Opening Balance` مع ملاحظة مصدرها واسم الورقة. لا تعتبر التواريخ المكتوبة في اسم الورقة تاريخ حركة.

لا تُرحّل أعمدة الإجمالي والمتبقي كحقائق مستقلة. يعاد حسابها من حركة الافتتاح، أو تسجل فروقاتها كمشكلات تحتاج اعتمادًا.

## 11. الترخيص Offline License

### 11.1 بنية الترخيص

يكون الترخيص ملفًا أو نصًا موقّعًا رقميًا، وليس تاريخًا محفوظًا فقط في قاعدة البيانات. يتضمن على الأقل:

- `productId`.
- `customerId`.
- `licenseId`.
- `issueDate`.
- `expiryDate`.
- `licenseType`.
- `version`.
- `signature`.

صيغة المفتاح الظاهر للمستخدم يمكن أن تكون مقروءة مثل `SOLI-XXXX-XXXX`، لكنها ليست خوارزمية التوقيع. يفضل أن تكون الحمولة الداخلية JSON canonical أو بنية ثنائية مستقرة، ثم توقّع خارج البرنامج.

### 11.2 التوقيع والتحقق

يحتوي البرنامج على Public Key فقط. يحتفظ مُصدر التراخيص بـ Private Key خارج البرنامج وفي بيئة إصدار محمية. يقترح استخدام Ed25519 من مكتبة تشفير موثوقة ومضمّنة، أو ECDSA/RSA وفق ما يثبت الاختبار والمكتبة المعتمدة على Windows 7. لا تستخدم كلمة مرور أو Hash وحده لإثبات صحة الترخيص.

عند التفعيل يتحقق البرنامج من التوقيع، و`productId`، و`version`، وتاريخ البداية، وتاريخ الانتهاء، وعدم تكرار `licenseId` بطريقة غير متسقة.

### 11.3 حالة الترخيص المحلية

ينشئ البرنامج سجلًا محليًا محميًا يتضمن آخر تشغيل، وآخر تاريخ معروف، ومعرف الترخيص الحالي، وتوقيعًا أو HMAC محليًا. هذا السجل يساعد في كشف الرجوع غير المنطقي للتاريخ، لكنه لا يجعل الحماية مطلقة.

عند اكتشاف رجوع في تاريخ Windows:

- لا تحذف البيانات.
- لا تعدل الحركات.
- توقف العمليات الحساسة.
- تسمح بالنسخ الاحتياطي.
- تعرض رسالة واضحة.
- تسمح بالتصحيح أو بإعادة التفعيل وفق سياسة الإصدار.

عند انتهاء الترخيص، تبقى البيانات وقاعدة البيانات والحركات محفوظة. يمنع النظام العمليات التشغيلية التي تحددها سياسة الترخيص، لكنه يسمح بالدخول إلى شاشة الترخيص، وإنشاء Backup، وإدخال مفتاح تجديد صحيح.

> الترخيص Offline لا يمكن جعله غير قابل للكسر بنسبة 100% لأن البرنامج يعمل محليًا وتوجد إمكانية نظرية لتحليل ملفاته. الهدف الواقعي هو منع الاستخدام غير المصرح به عمليًا بواسطة توقيع رقمي، وتقليل فرص العبث، وحماية بيانات العميل من الفقد.

## 12. الصلاحيات وRBAC

تطبق الصلاحيات على مستوى الشاشة والفعل والمخزن. وجود صلاحية View لا يمنح صلاحية Create، ووجود صلاحية Create لا يمنح صلاحية Approve.

| الدور | النطاق الافتراضي |
|---|---|
| ADMIN | إدارة كاملة، مع عدم حذف الحركات المعتمدة فعليًا |
| STORE_MANAGER | إدارة عمليات المخازن المصرح بها واعتمادها وفق السياسة |
| STORE_USER | إنشاء المسودات وإدخال البيانات دون اعتماد نهائي إلا إذا منح صراحة |
| VIEWER | عرض وتقارير وتصدير حسب الإعداد |

الأفعال الرئيسية هي View وCreate وUpdate وDelete/Void وApprove وExport وBackup وRestore. فعل Delete يعني حذف Draft أو إلغاء كيان غير معتمد، ولا يعني حذف حركة معتمدة.

يجب أن يتطلب Restore وManage Users وManage License صلاحية إدارية منفصلة. كل محاولة مرفوضة بسبب الصلاحية تسجل في Audit Log عند الحاجة الأمنية.

## 13. النسخ الاحتياطي والاستعادة

### 13.1 النسخ

يدعم النظام Backup يدويًا وBackup تلقائيًا اختياريًا عند تشغيل البرنامج أو إغلاقه، مع إمكانية تحديد مجلد محلي أو USB. يحتفظ النظام بعدة نسخ وفق عدد أو مدة يحددها المسؤول.

ملف النسخ يجب أن يحتوي على:

- نسخة قاعدة البيانات.
- رقم إصدار Schema.
- وقت الإنشاء.
- إصدار التطبيق.
- حجم الملف.
- Hash للتحقق من السلامة.
- هوية المخزن أو العميل عند الحاجة.

### 13.2 الاستعادة

قبل الاستعادة، يتحقق النظام من سلامة الملف، ونسخة Schema، ووجود الجداول الأساسية، وإمكانية فتح SQLite، وعدم وجود تلف. ينشئ Backup تلقائيًا للبيانات الحالية قبل استبدالها. لا يسمح بالاستعادة فوق البيانات الحالية دون شاشة تأكيد صريحة تعرض اسم النسخة وتاريخها وحجمها.

بعد الاستعادة، يسجل النظام العملية في Audit Log ويطلب إعادة تشغيل التطبيق. لا يخلط النظام بيانات النسخة مع البيانات الحالية في عملية غير واضحة.

## 14. التقارير والتصدير

التقارير الأساسية هي:

- الرصيد الحالي حسب المخزن.
- بطاقة حركة الصنف.
- حركات فترة زمنية.
- التوريدات.
- التحويلات.
- الصرف والاستهلاك.
- فروقات الجرد.
- الأصناف تحت الحد الأدنى.
- الأصناف ذات الرصيد السالب أو الاستثناءات.
- سجل التدقيق.
- حالة الترخيص والنسخ الاحتياطي.

يتم التصدير إلى Excel أو PDF من نتائج الاستعلام المعتمدة، مع إظهار وقت الإنشاء والمستخدم والفلاتر المستخدمة. لا يسمح التصدير بتعديل قاعدة البيانات.

## 17. خطة الاختبار

### 17.1 اختبار التقنية والتثبيت

يختبر الفريق تثبيتًا نظيفًا دون إنترنت على Windows 7 SP1 32-bit و64-bit، وWindows 8.1، وWindows 10، وWindows 11. يتحقق الاختبار من عدم الحاجة إلى Node.js أو Python أو Browser أو اتصال خارجي.

### 17.2 اختبار قاعدة البيانات

يتحقق الاختبار من المفاتيح الأجنبية، ومنع الصنف المكرر، ومنع الوحدة غير الصحيحة، وسلامة المعاملات، وإعادة بناء الرصيد من الحركات، وعدم وجود رصيد مخزن مستقل يختلف عن الحقيقة.

### 17.3 اختبار الحركة

يختبر الفريق التوريد، والتحويل، والصرف، والاستهلاك، والجرد، ومنع الرصيد السالب، وفشل التحويل في منتصف العملية، والتأكد من عدم بقاء حركة مصدر دون حركة وجهة.

### 17.4 اختبار Append-only وAudit

يحاول الاختبار تعديل وحذف حركة Approved بحسابات مختلفة. النتيجة المطلوبة هي الرفض، مع توفير مسار عكس موثق. يتحقق الاختبار من ظهور المستخدم والوقت والسبب في Audit Log.

### 17.5 اختبار Excel

يستخدم الاختبار نسخة من ملف `جردالمخازنوالطوارئوالعمليات.xlsx`، ولا يكتب فوق الأصل. يتحقق من اكتشاف التكرارات، والصفوف العنوانية، والخلايا الفارغة، والأرقام المفقودة، والوحدات غير الصحيحة، ومشكلة إجمالي ورقة الطوارئ، ثم يراجع المستخدم قائمة المشاكل قبل الترحيل.

### 17.6 اختبار الترخيص

يشمل الاختبار تفعيلًا صحيحًا، وتوقيعًا غير صحيح، وترخيصًا منتهيًا، وترخيصًا لمنتج مختلف، وتغيير الإصدار، وتغيير تاريخ Windows إلى الخلف، وتجديد الترخيص، وانتهاء الترخيص مع التأكد من بقاء البيانات والقدرة على Backup.

### 17.7 اختبار Backup/Restore

يشمل الاختبار نسخًا متعددة، ونسخة إلى USB، ونسخة تالفة، ونسخة من إصدار أقدم، واستعادة فوق بيانات موجودة، وانقطاع التشغيل أثناء النسخ. يجب أن ينتج كل اختبار نتيجة واضحة ومسجلة.
